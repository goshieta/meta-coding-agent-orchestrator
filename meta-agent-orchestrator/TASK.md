# TASK.md — Meta-Agent Orchestrator 実装タスク一覧

## 前提

- すべての実装は `/workspace/meta-agent-orchestrator/` 配下に行う。
- `PLAN.md` が本プロジェクトの最終仕様書である。各タスクは `PLAN.md` の該当機能（`F-xx`）を満たすこと。
- 各タスク完了後、README.md を最新の実装に合わせて更新し、動作テストを行うこと（AGENTS.md 準拠）。
- 各タスクは**他のエージェントが単独で実装し、次のタスクへ引き渡せる**よう、入出力・達成基準を明確に定義している。

## 全体構成（実装完了時の想定ディレクトリ）

```
meta-agent-orchestrator/
├── pyproject.toml            # uv による環境定義
├── README.md                 # プロジェクト概要・使い方（常に最新）
├── run-spec.sh               # ワンライナー起動スクリプト（F-01）
├── Dockerfile                # コンテナ隔離実行（F-02）
├── src/orchestrator/
│   ├── __init__.py
│   ├── config.py             # 設定管理（F-09 / F-12）
│   ├── cli.py                # CLI 入口・引数解析・仕様書検証（F-01）
│   ├── context.py            # コンテクスト構築（F-03 / F-10）
│   ├── planner.py            # 計画・タスク分解・共有ボード生成（F-04）
│   ├── executor.py           # 実装ループ（F-05）
│   ├── qa.py                 # 品質保証（F-06）
│   ├── deliver.py            # 完了・納品・GitHub push（F-07 / F-11）
│   ├── human_gate.py         # 人間インターフェース（F-08）
│   ├── tools/
│   │   ├── __init__.py
│   │   └── pi_tools.py       # pi連携 CrewAI Tool群
│   ├── agents/
│   │   ├── __init__.py
│   │   └── crew.py           # 各 Agent / Task / Crew（Process.HIERARCHICAL）
│   └── workspace.py          # 共有ボード・ログ・状態管理
└── tests/                    # 各タスクのテスト
```

> 上記は目安である。可読性・責務分離を保てば、実装エージェントが適切に構造化してよい。ただし各タスクの「達成基準」は必ず満たすこと。

## Task 1: プロジェクト雛形・環境構築

**目標**: Pythonプロジェクトの骨格を作り、以降のタスクが作業できる土台を整える。

**具体的にやること**
- `meta-agent-orchestrator/` 内に `pyproject.toml` を作成し、`uv` による環境管理を設定する（Python 3.x）。
- 依存ライブラリを宣言する：`crewai`（Agent/Task/Crew/Process）、CLI・ロギング・環境変数読み込み用のライブラリ（例: `python-dotenv`）。
- パッケージ用ディレクトリ `src/orchestrator/` と `tests/` を作成する。
- `main` 相当の最小エントリポイント（例: `orchestrator/main.py`）を用意し、`python -m orchestrator` で起動確認できるようにする。
- 空の `README.md` を作成し、プロジェクト概要のひな形を書く（後続タスクで随時更新）。

**入出力**
- 入力: なし（新規作成のみ）
- 出力: `pyproject.toml`・`src/orchestrator/`・`tests/`・`README.md`

**達成基準**
- `uv run python -m orchestrator` がエラーなく起動し、ヘルプまたは挨拶メッセージを表示する。
- `uv run pytest tests/` がエラーなく実行できる（ダミーテスト1件以上）。

**引き渡し条件**: 環境構築が `uv` で再現可能であること（`uv sync` で再現できる）。

## Task 2: 設定管理（Config）※外部化

**目標**: モデル割当・GitHubトークン・作業ディレクトリ等の全設定を外部から制御できるようにする（F-09 / F-12）。

**具体的にやること**
- `config.py` を実装し、以下を扱うこと：
  - 環境変数: `AGENT_ORCHESTRATOR_MODEL` / `AGENT_EXEC_MODEL` / `AGENT_QA_MODEL` / `AGENT_SURVEY_MODEL` / `GITHUB_TOKEN` / `PI_SESSION_DIR` / `PI_PROVIDER` / `PI_THINKING` / `PI_TRUST`（trust制御）。
  - CLI引数: `--orchestrator-model` / `--exec-model` / `--qa-model` / `--survey-model` / `--github-token` 等で個別上書き。
  - 解決優先順位: **CLI引数 > 環境変数 > デフォルト値**。
  - 役割別デフォルトモデル（PLAN F-12: オーケストレータ=コスパ系、実行=中〜高性能、QA=高性能、調査=コスパ系）を外部設定で上書き可能にしておく。
- 設定オブジェクト（例: `OrchestratorConfig` dataclass）に集約し、全モジュールから参照できるようにする。

**入出力**
- 入力: 環境変数 / CLI引数
- 出力: 単一の設定オブジェクト

**達成基準**
- テストで「環境変数なし→デフォルト」「環境変数あり→環境変数」「引数あり→引数優先」の各ケースを検証できる。
- 全モデル・トークン・セッション系設定が外部から注入可能である。

## Task 3: CLI エントリポイントと仕様書検証（F-01）

**目標**: `run-spec.sh <spec.md> [existing_repo/]` のワンライナー起動を実現し、入力を検証する。

**具体的にやること**
- `cli.py` を実装し、引数（`spec.md` 必須 / `existing_repo/` 任意 / 各モデル上書きフラグ）を `argparse` 等で解析する。
- `run-spec.sh`（実行可能・shebang付き）を作成し、`uv run` 経由で Python 側エントリを起動する薄いラッパーにする。
- 仕様書検証: 引数未指定・ファイル不存在・空ファイルの場合は**エラーメッセージを出して即終了**（exit code 非0）。
- 起動成功時はコンテナID・ログパスを出力する（Task 7 のコンテナ対応後はその値を出す。それまではログパスのみ）。
- Task 2 の設定を読み込み、仕様書パス・既存リポジトリパス・モデル設定を後続パイプラインへ引き渡す。

**入出力**
- 入力: CLI引数
- 出力: 検証結果・起動開始・（コンテナ化後は）コンテナID・ログパス

**達成基準**
- `run-spec.sh`（または `uv run` 直叩き）で「仕様書なし→即終了」「存在しないファイル→即終了」を確認できる。
- 有効な仕様書指定でパイプラインが開始される。

## Task 4: pi 連携 CrewAI Tool 群（F-05 の基盤）

**目標**: マネジメント層から pi プロセスを操作するための CrewAI Tool 群を実装する（Manager-only 原則の実行体）。

**具体的にやること**
- `tools/pi_tools.py` を実装し、pi を subprocess で呼び出す以下の Tool を提供する：
  - `run_pi_single`: `pi -p @spec.md "タスク"` のワンショット実行
  - `run_pi_continue`: `pi -c` / `--fork <id>` / `--session <id>` によるセッション継続
  - `run_pi_fork`: 失敗時・再実行時に `--fork` で新セッション生成
  - `compact_context`: `/compact` でコンテクスト解放
  - `export_session`: `/export` で JSONL 化して永続化
- 各 Tool は外部設定から `--provider` / `--model` / `--thinking` / trust制御（`--approve` / 相当）を付与する。
- **Manager-only 原則に従い、Toolは pi を介してのみ作業を行い、マネジメント層エージェントはコードに直接アクセスしないこと。**
- 実行時の stdout/stderr・exit code を自然言語レポートとして返し、オーケストレータが消費できるようにする。

**入出力**
- 入力: タスク指示（自然言語）/ セッションID / モデル設定
- 出力: pi の実行結果レポート（自然言語 + exit code）

**達成基準**
- 各 Tool が存在し、テスト用に pi の利用可否や引数構成を検証できる。
- 失敗時は exit code とエラー内容が Tool の戻り値に含まれる。

## Task 5: ワークスペース・共有ボード・状態管理

**目標**: 共有ボード（`plan.md`）・タスク別ログ・セッション保存を管理する共通基盤を作る（F-04 / F-05 / 冪等性）。

**具体的にやること**
- `workspace.py` を実装し、以下を提供する：
  - 作業ディレクトリ（`workdir`）の生成・管理。
  - 共有ボード `plan.md` の読み書き（タスク一覧・状態・依存・優先度）。
  - タスク別ログの保持（`logs/<task>.log` 等）。
  - pi セッション（`--session`）・`/export` による JSONL 永続化を、再起動（冪等性）で復元できるよう管理する。
- ボードの状態遷移（例: `planned → running → done / failed → qa → done`）を定め、状態を追跡できるようにする。

**入出力**
- 入力: タスク情報・進行イベント
- 出力: 更新後のボード・ログ・セッション永続化ファイル

**達成基準**
- `plan.md` を生成し、状態を更新・再読み込みできる。
- 再起動時に前回のセッション・状態を復元できる（冪等性）。

## Task 6: コンテクスト構築（新規・既存）（F-03 / F-10）

**目標**: 仕様書を起点に pi へ投入する初期コンテクストを構築し、既存案件では現状把握レポートを生成する。

**具体的にやこと**
- `context.py` を実装する：
  - **新規**: 仕様書を pi 初期プロンプトとして投入（`pi @spec.md "..."`）。AGENTS.md / システムプロンプトを活用する。
  - **既存**: 第2引数のコードベースを対象に、調査エージェントが pi（読み取り専用ツール `--tools read,grep,find,ls`）経由で解析し、**現状レポート**を生成する。
  - 生成したコンテクスト・現状レポートを共有ボード・作業ディレクトリへ保存する。

**入出力**
- 入力: 仕様書パス / 既存リポジトリパス（任意）
- 出力: 初期コンテクスト / 現状レポート

**達成基準**
- 新規・既存どちらの経路でも、タスク分解に必要なコンテクストが揃う。
- 既存経路では現状レポートが生成され、オーケストレータが自然言語で参照できる。

## Task 7: コンテナ隔離実行（F-02）

**目標**: 全エージェント・pi プロセスをコンテナ内で稼働させ、ホストを非汚染に保つ。

**具体的にやること**
- `Dockerfile` を作成し、Python/uv・pi・CrewAI 実行環境をコンテナに組み込む。
- 既存リポジトリを第2引数でコンテナへマウントする仕組み（除外ファイル考慮）を設ける。
- 起動時のみ環境変数（モデル割当・`GITHUB_TOKEN` 等）を注入し、イメージにトークンを埋め込まない。
- ワークスペース・セッション・ログを永続ボリューム／マウントで保持し、**再起動でも状態を保つ（冪等性）**。
- `run-spec.sh` からコンテナを起動し、コンテナIDとログパスを出力する。

**入出力**
- 入力: 仕様書 /（任意）既存リポジトリ / 環境変数
- 出力: 稼働コンテナ / コンテナID / ログパス

**達成基準**
- コンテナ内で pi・CrewAI が動作する。
- ホストのファイル・環境が汚染されない。
- `docker rm` / 再起動後もセッション・ログが復元できる。

## Task 8: CrewAI エージェント群とクルー構成（Process.HIERARCHICAL）

**目標**: オーケストレータ・実行・QA・調査の各エージェントを定義し、HIERARCHICAL クルーとして組み立てる。

**具体的にやること**
- `agents/crew.py` を実装する：
  - **オーケストレータ（manager）**: 戦略・タスク分解・最終判定。コスパ系モデル。
  - **実行インターフェーサー**: Task4 の pi Tool を使って実装を進める。中〜高性能モデル。
  - **QAクリティック**: 批判的視点で検証。高性能モデル。
  - **調査エージェント**: 既存コード把握。コスパ系モデル。（必要時のみ）
- 全エージェントに Task4 の pi Tool を共有させる（実装・検証・調査）。
- クルーを `Process.HIERARCHICAL` で構成し、オーケストレータが manager として振る舞うようにする。
- **Manager-only 原則を厳守**し、エージェントは pi Tool 経由のみでコードに触れること。
- 各エージェントの System Prompt / 役割記述を明確に定義する。

**入出力**
- 入力: コンテクスト / 共有ボード / タスク
- 出力: 実行可能な Crew（`crew.kickoff()` 等で駆動）

**達成基準**
- クルー構成コードが存在し、エージェント・タスク・プロセス定義が確認できる。
- 各エージェントのモデル割当が Task2 の設定から注入される。

## Task 9: 実装ループ（F-05）

**目標**: タスクを順に実行し、pi へ指示・レポート回収・コミットを行うループを実装する。

**具体的にやること**
- `executor.py` を実装する：
  - 共有ボードのタスクを依存・優先度順に実行する。
  - 実行インターフェーサーが pi Tool（`run_pi_single` / `run_pi_continue`）で実装し、自然言語レポートを回収してオーケストレータへ報告する。
  - 進行中の指示注入（steering / follow-up）を可能にする。
  - 必要に応じ `/compact` でコンテクストを解放し肥大を防ぐ。
  - **タスク完了ごとに commit**（過程を追跡）。
  - 失敗したタスクは Task4 の fork で再実行する。
- タスク別ログを共有ボード・ワークスペースへ記録する（Task5 を利用）。

**入出力**
- 入力: タスク一覧 / 各タスクのコンテクスト
- 出力: 実装済みコード / タスク状態（done/failed） / コミット履歴 / レポート

**達成基準**
- タスク完了ごとに commit が生成される。
- 失敗タスクが再実行され、状態がボードに反映される。
- レポートがオーケストレータへ自然言語で返る。

## Task 10: 品質保証（独立QAクリティック）（F-06）

**目標**: 独立コンテクスト・批判的視点の QA クリティックが成果物を検証し、問題を実装ループへ再送する。

**具体的にやること**
- `qa.py` を実装する：
  - QAクリティックが pi Tool（検証）で成果物を検証する。**オーケストレータとは独立したコンテクスト・批判的視点**を持つ。
  - 検証結果を問題リストとして返す。
  - 問題あり → 該当タスクを Task9 の実装ループへ再送。
  - 通過 → 次のフェーズ（完了・納品）へ進む判定を出す。
- QA 判定基準（テスト実行・仕様充足・可読性等）を明確に定める。

**入出力**
- 入力: 実装済み成果物 / 仕様書
- 出力: 検証レポート（問題リスト or 合格） / 再送要求

**達成基準**
- QA レポートが生成され、問題時は再送ルートが動作する。
- `main.py` / `pytest` 等で実装が動く確認を行う。

## Task 11: GitHub アップロードと完了・納品（F-07 / F-11）

**目標**: 全タスク完了時、オーケストレータが最終判定し、**一度だけ**リポジトリ作成→push を行う。

**具体的にやること**
- `deliver.py` を実装する：
  - 全タスク・QA 通過を確認し、オーケストレータが最終判定する。
  - GitHub へリポジトリを作成し、**一度だけ** push する（token 注入・認証はコンテナ内で管理。Task7 と整合）。
  - push 実施を冪等に管理し、二重 push を防ぐ（完了フラグ/ボード記録）。
  - 人間の最終承認を待ってから停止する（Task12 と連携）。
- 認証失敗・push 失敗時のエラーハンドリングを実装する。

**入出力**
- 入力: 合格した成果物 / GitHubトークン
- 出力: 作成・push 後の GitHub リポジトリ / 完了通知

**達成基準**
- 全タスク+QA 通過後に一度だけ push される。
- 二重 push を防げる（冪等）。
- 失敗時は明確なエラーと状態保持で再実行可能。

## Task 12: 人間インターフェース（質問提出・強制停止）（F-08）

**目標**: 人間との最小限の接点（質問提出・強制停止）を実装する。

**具体的にやること**
- `human_gate.py` を実装する：
  - 仕様の過不足時、エージェントが人間へ質問を提出し、応答を待つ。
  - 人間→エージェントの**強制停止コマンド**を受け付け、**状態を保存して安全に停止**する（再開可能）。
- 強制停止後も共有ボード・セッション・ログ（Task5）を保持し、再開できるようにする。

**入出力**
- 入力: 人間からの応答・停止コマンド
- 出力: エージェントへの質問回答 / 安全停止

**達成基準**
- 質問→応答→続行、および強制停止→状態保存→（再開可能）の流れが動作する。
